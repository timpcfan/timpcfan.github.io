今天晚上，我把个人网站的一批历史静态资源，从百度云 BOS 迁移到了 Cloudflare R2。

这件事说起来，核心动机其实一点也不高大上，主要就是四个字：**能省则省**。

## 为什么要迁

### 1. 费用问题，以及一点朴素的白嫖精神

之前我个人网站的图片和一些静态资源，是放在百度云 BOS 上的。它当然不是不能用，只是它本质上还是一个**需要付费**的对象存储方案。

而我这种个人网站，很多时候并不追求什么复杂企业级能力，想要的就是一个足够稳定、足够省心、最好还能尽量少花钱的资源托管方案。

所以很自然地，我就开始想：既然有机会白嫖，为什么不白嫖？

### 2. R2 的免费额度更香

这次迁移去 Cloudflare R2，其实是派蒙推荐的。也就是我的 OpenClaw 助手。

它提醒我，Cloudflare R2 有每个月的免费额度，对于我这种个人网站的资源规模来说，已经相当够用了。这个建议一出来，我就很心动。毕竟相比继续把资源挂在一个长期付费、但自己又没有那么高依赖的存储服务上，迁到一个**有免费额度、而且访问链路也更适合静态资源分发**的地方，怎么看都更顺手。

于是这件事就从“以后有空再说”，变成了“今晚就把它干掉”。

### 3. 意外找回一批我以为已经丢了的资源

更有意思的是，在真正开始迁移之前，我本来一直以为这批图片和静态资源早就没了。

因为百度云那边我已经很久没续费，也很久没有认真维护过。我原本默认它们大概率已经被自动清理，或者至少已经彻底失效了。

结果今天重新打开百度云控制台一看，发现它们**居然都还在**。

只是状态很微妙：资源本体还在对象存储里，但已经**不能直接通过公网访问**了。也就是说，文件没有真正消失，只是从“还能直接拿来用”，变成了“你得进后台自己想办法把它们捞出来”。

某种意义上，这也算是一种意外的资源打捞。

### 4. 这时候，能接管浏览器的派蒙就特别好用

接下来最麻烦的问题就来了：怎么把这些旧资源完整拿下来？

按理说，最理想的情况当然是对象存储后台直接提供一个很顺手的**批量下载**按钮，我点一下就结束了。但实际情况是，这个控制台页面并没有给我一个足够省事的批量下载入口。至少在我这次操作的路径上，没有一个让我满意的“一键全下”。

于是我就干脆把这件事交给派蒙来做：

1. 先接管浏览器页面；
2. 进入对象存储目录；
3. 一页一页翻；
4. 一个一个把资源点下来；
5. 再把项目里引用到的链接全部核对一遍。

这种事情如果纯手动做，不能说做不了，但真的非常消耗耐心，而且很容易漏。尤其是当资源跨了很多分页、文件类型还不完全一致的时候，人肉做重复点击简直是在消耗生命。

这时候派蒙就非常好用了。把浏览器接上之后，这类重复机械劳动就很适合交给它来跑。

而且这次它确实干得很漂亮：

- 先把资源逐页遍历出来；
- 把文件一批一批下载到本地；
- 再去扫描我个人网站项目 `timpcfan.github.io` 里所有对象存储链接；
- 把项目里引用到的对象名，和本地下载下来的文件逐个对账；
- 最后确认无误，再统一上传到 R2，并把旧链接全部替换掉。

## 最终结果

这次迁移最后收口得还挺干净。

对于 `timpcfan.github.io` 这个项目：

- 一共扫描到 **836 处**旧对象存储链接引用；
- 去重后，对应 **188 个**实际对象；
- 这些对象都能在本地下载结果中找到；
- 上传到 R2 时，**188 个对象全部成功上传，没有失败项**；
- 项目里的旧 BOS 链接也已经**全部替换完成**。

新的资源链接现在统一变成：

```text
https://img.timpcfan.site/imgs/<文件名>
```

也就是说，之后这个个人网站里原来那批依赖百度云 BOS 的静态资源，就正式迁移到了 Cloudflare R2。

## 一点很真实的感受

这次迁移做完之后，我最大的感受其实不是“技术上完成了一次资源迁移”，而是：

**原来很多你以为已经烂尾、已经失效、已经丢掉的历史资产，认真翻一下，还是有机会救回来的。**

另外还有一个很现实的体会：

如果一件事本质上是“重复、机械、容易漏”的，那么把它交给一个能稳定接管浏览器、能帮你核对上下文的助手去做，体验真的会好很多。至少今晚这一轮，派蒙确实帮我省掉了大量重复劳动。

这批资源总算搬完了。
以后这个网站的静态资源，也算是收拢到了一个我自己更愿意长期维护的地方。
