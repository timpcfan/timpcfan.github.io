# Lesson 07｜组织落地：把案例沉淀为 SOP，并让团队“用得起来”

## 核心问题
工具在你自己电脑上跑通，不等于能在团队里落地。组织落地最难的不是写代码，而是：
- **协作边界**：谁触发、谁停止、失败怎么兜底，避免“机器人自己聊嗨了/失控刷屏”。
- **接入验收**：第三方能力（token/登录态）如果没走完验收，就会变成“装了但不能用”。
- **SOP 的可执行性**：规则如果写成口号（例如“注意稳定性”），对团队没有增益。

## 错误尝试 / 失败点
1) **没有触发门禁**：机器人会在“无任务”的聊天里继续输出，导致干扰与信任崩塌。
2) **没有刹车机制**：连续报错时不停止，会形成错误循环，把群刷爆。
3) **只写‘安装成功’不做‘验收成功’**：第三方技能最常见失败不是安装，而是 token/登录态没配置。
4) **SOP 不可执行**：写一堆原则，没人知道“下一步具体按什么命令/按什么顺序做”。

## 关键转折
组织落地的转折点是：
- 把“协作”抽象成**状态机**（触发 → 执行 → 结束/暂停），而不是聊天式自由发挥；
- 把“接入”抽象成**交付物**：配置文件落地 + API 级联调证据，而不是“我感觉可以”。

## 可复用 SOP（团队推广模板）
> 目标：任何人都能用同一套规则把一个自动化能力推广到团队。

### SOP-1：协作协议（防失控）
1) Trigger Gate：仅当消息包含 `#task` / `#sync` / `继续` 才启动流程。
2) 非触发场景：最多回复一次 `HOLD`，然后停止。
3) TIMEOUT：90 秒无响应则暂停（标记为 TIMEOUT）。
4) FAIL-STOP：连续 3 次技术错误，强制 STOP，并记录最后一次错误摘要。
5) 交付即停：交付后一次确认就结束（Stop），避免链路拉长。

### SOP-2：第三方能力接入（从“可安装”到“可用”）
1) 安装：能自动化就自动化（但不要把“安装成功”当终点）。
2) 缺口定位：如果不可用，优先检查 token/登录态。
3) 凭据落地：写入 `~/.config/openclaw/<service>.env`，权限 600。
4) API 级验收：必须有“HTTP 200 + success=true”（或等价成功信号）。
5) 业务级验收：用 1 个真实场景跑通（场景 Unknown 也要写清为什么 Unknown）。
6) 文档化：把“拿 token 的入口 + env 文件名 + 验收信号”写进团队 SOP。

## 课后作业
1) 选一个你们团队正在用的机器人/脚本，给它补上 4 个状态：触发门禁、HOLD、TIMEOUT、FAIL-STOP，并写成一页 SOP。
2) 选一个需要 token 的第三方服务，按“落盘 + API 验收 + 业务验收”跑一遍，把证据（成功信号）贴进文档。
3) 讨论题：你们团队更适合“默认沉默，只有异常才通知”，还是“固定窗口播报”？写出理由；不确定就写 Unknown。
