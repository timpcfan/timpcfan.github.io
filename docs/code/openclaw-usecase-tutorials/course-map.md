# Course Map｜OpenClaw 用例工程递进课程（Part 0~4）

> 目的：这是“总纲 + 目录 + 证据来源映射”。不写长正文；正文里会把每条映射展开为：真实场景 → 失败点 → 关键转折 → SOP → 作业，并附 sessionKey/time/quote。

## Part 0｜从“能跑”到“可复用”：用例工程方法

### Lesson 0.1｜什么叫“可复用用例”？从一次成功到一套模板
- 核心问题：为什么“跑通一次”不等于“可复用”？怎样把成功沉淀为模板（reuse_template）？
- 你会产出的东西：一份用例卡（Problem / Workflow / Outcome / Reuse template / Unknowns / Tags）。
- 证据来源映射（用例标题）：
  1) Codex 多账号额度巡检与 auth order 自动重排
  2) 每小时 Stash 网络探测 + 异常才通知
  3) 30G 诊断日志膨胀的止损修复：删文件 + 关 cacheTrace + 回归验证

### Lesson 0.2｜证据驱动：如何用 sessionKey/time/quote 给结论上“钢印”
- 核心问题：团队分享里，如何避免“我感觉/应该是”？怎样把结论锚定到可回放的证据？
- 你会产出的东西：一份“证据锚点”写作规范（每个关键结论 ≥1 个 quote）。
- 证据来源映射：
  1) 会话驱动自进化：24h 信号采集并更新 skill-gaps
  2) 争议信息用‘实测 + 官方规则页’双证据定性

## Part 1｜失败是主线：把常见故障变成可自动降级的 SOP

### Lesson 1.1｜检索链路三连击：429 + fetch failed + 本地命令错误
- 核心问题：当检索层（429/抓取失败）和执行层（python 不存在）同时炸时，如何让任务仍能“按时交付”？
- 你会产出的东西：一份“分级故障处置表”（检索失败→DDG 兜底；命令失败→解释器修正）。
- 证据来源映射：
  1) Brave 429 + fetch failed + python 命令错误的多故障串联修复
  2) AI 公司动态监控：检索退避 + 多源兜底 + 24h 时窗

### Lesson 1.2｜web_fetch 被私网 IP 策略拦截：如何无痛切换抓取链路
- 核心问题：当 web_fetch 报 “Blocked: resolves to private/internal/special-use IP address” 时，怎样保持任务不断线，并且让降级路径可复用？
- 你会产出的东西：一份“抓取链路路由器”SOP（web_fetch → browser 抓取 → web_search 补证 → 原投递链路不变）。
- 证据来源映射：
  1) web_fetch 被私网 IP 策略拦截后，切换抓取链路完成定时播报
  2) 同类私网拦截在另一条 cron 复现，验证 fallback 可复用
  3) AI 公司动态监控：检索退避 + 多源兜底 + 24h 时窗

### Lesson 1.3｜FakeIP 环境下的诊断纠偏：别再被 dig/nslookup 带沟里
- 核心问题：为什么在代理 FakeIP 环境下，DNS 结果可能是“假象”？如何建立“真实访问链路优先”的排障规则？
- 你会产出的东西：一份团队级排障 SOP（禁止单看 DNS；必须用浏览器实测/代理内链路复测）。
- 证据来源映射：
  1) FakeIP 网络环境下的诊断纠偏流程

## Part 2｜监控与播报：做“异常优先、不刷屏”的 cron 体系

### Lesson 2.1｜每小时巡检不等于每小时刷屏：通知门禁怎么做
- 核心问题：如何在“持续监控”和“群里不被刷屏”之间做工程化平衡？
- 你会产出的东西：一份“通知门禁”设计（异常才发 + 提醒窗口 + threadId 归档）。
- 证据来源映射：
  1) 每小时 Stash 网络探测 + 异常才通知
  2) AI 公司动态监控：检索退避 + 多源兜底 + 24h 时窗

### Lesson 2.2｜cron 失败后的快速复盘 + 手动补跑闭环
- 核心问题：cron 失败时，怎样快速回答三个问题：失败发生在何时？为什么失败？现在如何立刻恢复可信结果？
- 你会产出的东西：一份“失败复盘模板”（时间窗口 + 错误原因 + 抗抖参数建议 + 立刻补跑回执）。
- 证据来源映射：
  1) Cron任务异常后快速复盘 + 手动补跑闭环
  2) Gateway 超时抖动场景下，用可用读操作维持诊断闭环

### Lesson 2.3｜双目录 Git 自动备份：失败可见化、结果可追踪
- 核心问题：当要备份两个关键目录时，如何保证“谁成功谁失败一眼可见”，并且保留可追踪的 commit 证据？
- 你会产出的东西：一份“多目标任务统一汇总格式”（成功/失败/无变更 + 原因 + hash）。
- 证据来源映射：
  1) 双目录 Git 自动备份 + 失败可见化播报

  1) 30G 诊断日志膨胀的止损修复：删文件 + 关 cacheTrace + 回归验证

- 证据来源映射：

- 核心问题：为什么“装上了”不等于“能用”？如何把 token/登录态这个最大不确定性，变成可审计、可验证的上线流程？

- 证据来源映射：
  1) Codex 多账号额度巡检与 auth order 自动重排
  2) Cron任务异常后快速复盘 + 手动补跑闭环

### Lesson 4.2｜Overnight Goal Autopilot：夜间无人值守也能产出“行动包”
- 核心问题：怎么让“长期目标”不再停留在口号，而是每天自动产出可执行文档，并形成连续迭代节奏？

### Lesson 4.3｜会话驱动自进化：24h 信号采集并更新 skill-gaps

  1) 会话驱动自进化：24h 信号采集并更新 skill-gaps
